# Interacting Shells in AdS Revisited

[Repository](https://github.com/u39kun/ads-two-shell-chaos) · [Zenodo archive, v1.0](https://doi.org/10.5281/zenodo.23724493) · [MIT license](LICENSE) · [Citation metadata](CITATION.cff)

Code and results for **"Interacting shells in anti-de Sitter space revisited: an invariant measure, regular orbits, and chaos"** (Yusaku Sako). The paper re-examines the two-shell model of Brito, Cardoso, and Rocha (BCR), [“Interacting shells in AdS spacetime and chaos”](https://doi.org/10.1103/PhysRevD.94.024003), *Phys. Rev. D* **94**, 024003 (2016) ([arXiv:1602.03535](https://arxiv.org/abs/1602.03535)).

## Code and data

The reference results were computed on an Intel Core i9-14900K (32 threads, AVX2), with Python 3.13 on Ubuntu 24.04. The repository includes saved results in `results/` and reference figures, tables, and quoted numbers in `figs/`. Exact reproduction on AVX-512 Xeon and AMD Zen 4/5 processors requires the [settings below](#match-the-reference-results). See [Tested machines](#tested-machines) for the processors and cloud instances tested.

Exact reproduction means that the quoted numbers, figures, and tables match the reference. Inconsequential differences in logged run times or other metadata-only differences may remain.

### Setup and common workflows

#### Install the environment

On Ubuntu 24.04, install Python 3.13 if needed:

```bash
sudo add-apt-repository ppa:deadsnakes/ppa
sudo apt install python3.13 python3.13-venv
```

```bash
git clone https://github.com/u39kun/ads-two-shell-chaos
cd ads-two-shell-chaos
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

#### Match the reference results

On AVX-512 Xeon and AMD Zen 4/5 processors, apply these settings before rerunning results. See [Processor settings](#processor-settings) for details.

```bash
export NPY_DISABLE_CPU_FEATURES="X86_V4 AVX512_CLX AVX512_ICL AVX512_SPR"
export OPENBLAS_CORETYPE=Haswell
export NUMBA_CPU_NAME=haswell
# Required on AMD Zen 4/5; harmless on Intel.
export OPENBLAS_L2_SIZE=2048
```

#### Draw figures and generate tables from the saved results

Reference PDFs (Figures 1–10), LaTeX tables (Tables 1–4), and `figure_numbers.json` are included in `figs/`. Regenerate Figures 1–9, Tables 1–3, and their quoted numbers with:

```bash
python make_figures_bcr.py figs
```

Figure 10 and Table 4 are generated by the [addendum scripts](#addendum-checks-figure-10-and-table-4).

#### Run the full pipeline

```bash
# Use 32 worker processes; omit 32 to use all cores.
./run_all.sh 32

# Additional checks, Figure 10, and Table 4.
./addendum/run_addendum.sh
```

`run_all.sh` runs in dependency order, saves logs next to the results, and writes figures and quoted numbers to `figs_rerun/`. Existing results are skipped, so interrupted runs can resume. A full run takes about 90 minutes on the 32-thread i9-14900K; all timing estimates below are also for this machine.

Optional controls (choose the command you need):

```bash
# List commands without running them.
DRY=1 ./run_all.sh
```

```bash
# Rerun all steps, including those with existing results.
FORCE=1 ./run_all.sh
```

```bash
# Rerun selected steps; their inputs must already exist.
# Step names are listed in run_all.sh.
FORCE=1 STEPS="section checks" ./run_all.sh
```

#### Compare a rerun with the shipped results

```bash
mv results results-reference
./run_all.sh
python compare_results.py results-reference results
```

The comparison reports numerical and structural differences and writes figures from both sets of results to `figs_compare/`. Some shipped files lack metadata added by the current scripts; these appear as structural differences that do not affect reproducibility of the results. See [Interpreting cross-machine differences](#interpreting-cross-machine-differences) for what to expect without the processor settings above.

### Command reference

Use the blocks below to rerun individual figures or checks with the shipped inputs. For a full rebuild, use the pipeline above; it handles all dependencies. Commands write to the paths shown; `bcr_benettin_long.py` writes to `results/bcr_section/bcr_benettin_long.json`.

#### Dependencies, resuming, and parallelism

- Scans save per-case files next to their output (for example `results/bcr_section/delta_scan_parts/`) and resume interrupted runs. Cached cases are reused only when all parameters match.
- Parallel scripts use all cores by default; pass `--workers N` where the script accepts it.
- Some scripts read fixed paths under `results/` regardless of their arguments: `bcr_benettin_long.py` reads `bcr_section.json` and writes `bcr_benettin_long.json`; `bcr_jacobian_check.py` and `bcr_noise_trace.py` read `bcr_section.json`; `bcr_layer_tangent.py` reads `bcr_section.json`, `delta_scan.json`, `layer_delta.json`, or `layer_tangent_delta.json`, depending on its mode. `run_all.sh` handles this ordering.

### Numerical methods

#### Solvers and tolerances

- `n_shells.py` is the reference solver: thin shells in AdS4, DOP853 between crossings, event-located crossings, and the Ida–Nakao crossing rule.
- `fastshells.py` is a compiled (Numba) drop-in used for long runs. It takes the DOP853 coefficients from SciPy's private module `scipy.integrate._ivp.dop853_coefficients`.
- Unless a script or its refinement test states otherwise, the relative tolerance is 1e-12, the maximum step is 0.02, and the absolute tolerance is 1e-2 times the relative tolerance (1e-14 at the default), multiplied by delta/0.03 in scans of the type (ii) family.
- Scripts that integrate through `n_shells.simulate` use the compiled solver by default; `SOLVER=reference` switches them to the reference solver. `bcr_lyapunov.py`, `two_shell_measure.py`, and `independent_check.py` always use the reference solver. Scripts built on `tangent_map.py` use its own integrator.

#### Independent implementation and tangent map

`independent_check.py` is a second implementation, written separately, that compares against both solvers (`results/paper/independent_check.json`). It shares the physical model (junction condition, transparent crossings, and the clock of the middle region) with the reference solver, as well as SciPy's DOP853 and event location on dense output. The compiled solver instead locates crossings by regula falsi on re-integrated steps.

The independent implementation differs in its variables (R and dR/dt, BCR's Eq. 14, instead of R and dR/dtau with lapse matching), potential (solved symbolically from the junction condition), and crossing rule (built from the jumps of grad R in a light-cone frame instead of the closed-form update).

`tangent_map.py` computes the section map together with its derivative (the variational tangent), using variational equations with complex-step right-hand-side Jacobians and saltation terms at crossings. It uses no finite differences.

### Environment and cross-machine reproducibility

#### Reference environment

The results in `results/` were computed with:

- Python 3.13.17 on Ubuntu 24.04.5 LTS, x86_64, on a 32-thread Intel Core i9-14900K (AVX2; `results/ENVIRONMENT.txt`).
- NumPy 2.5.3, SciPy 1.18.1, Numba 0.68.0 (llvmlite 0.50.0), Matplotlib 3.11.2, and SymPy 1.14.0, pinned in `requirements.txt`.

The whole pipeline has also been rerun from scratch with the pinned package versions on Intel Xeon and AMD EPYC processors (table below). These cross-machine runs used Python 3.13 on Ubuntu 24.04 (3.13.17; 3.13.18 on the c6i.8xlarge). Python 3.12 (Ubuntu 24.04's default) also reproduces identical results on the i9.

#### Processor settings

Results depend on the processor's instruction set. NumPy, OpenBLAS, and Numba choose a code path at run time, and AVX-512 and AVX2 code paths can round results slightly differently. The shipped results use AVX2; restricting an AVX-512 machine to those code paths reproduces them exactly on the tested machines.

The [exports above](#match-the-reference-results) select the AVX2 code paths in NumPy, OpenBLAS, and Numba for the current shell.

The OpenBLAS bundled with NumPy 2.5.3 (0.3.34) enlarges its matrix-multiply blocking on these AMD processors even when `OPENBLAS_CORETYPE` selects another kernel, which overflows a buffer in the Haswell kernel ([OpenBLAS #6021](https://github.com/OpenMathLib/OpenBLAS/issues/6021), fixed for 0.3.35). Without `OPENBLAS_L2_SIZE=2048`, `bcr_section_lyapunov.py` (App. C) crashes in `numpy.linalg.lstsq`; every other result file is still identical. The setting turns the enlarged blocking off and has no effect on Intel. `OPENBLAS_CORETYPE=Zen` crashes the same way; leaving OpenBLAS unrestricted avoids the crash but changes results because its AVX-512 kernels round differently.

#### Thread-count sensitivity

The result of `bcr_wba.py` at n = 8000 also depends on the number of logical CPUs. OpenBLAS splits long dot products (above about 1e4 terms) over as many threads as there are logical CPUs, and the split changes the last bits of the sums. The i9 has 32. On a machine with a different count, the convergence digits `n_vs_2n` at n = 8000 differ in the fifth significant figure. On a machine with at least 32 logical CPUs, the following setting should remove this difference (not tested):

```bash
export OPENBLAS_NUM_THREADS=32
```

#### Interpreting cross-machine differences

Between AVX2 and AVX-512 code paths:

- Along regular orbits the difference stays small. Their variational-tangent exponents are close to zero and changed by at most 2e-5 per return, so a small absolute change can be a large relative one. Two-orbit estimates near their noise floor change more (App. C).
- Along chaotic orbits differences grow exponentially. Individual trajectories and finite-time exponents agree only between runs using the same code paths. Across code paths, the exponents agree in typical size and the classification as chaotic or regular agrees except for one start at the threshold (App. C). The set of orbits selected by exponent for `tangent_extend` can also differ.

The unrestricted AMD EPYC AVX-512 rerun is archived in `reruns/amd-epyc-avx512_py3.13/`, including its results, environment, and comparison with `results/`. The Intel Xeon AVX-512 run is not archived separately because it gave the same results apart from the thread-count effect above; the AVX2-restricted runs are also not archived because they reproduce `results/` exactly.

```bash
# Compare the archived AVX-512 rerun with the shipped results.
python compare_results.py results reruns/amd-epyc-avx512_py3.13/results
```
